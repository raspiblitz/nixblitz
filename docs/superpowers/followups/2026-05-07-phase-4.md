## Cosmetic gaps in dashboard tiles

These are bindings the tile DSL declares but the streamer can't
populate from blitz-api's current SSE event surface.

### `chain_name` / `chain_color` (bitcoin tile Network row)

**Where it's bound:** `common/lib/src/services/dashboard/bundled/manifests/bitcoin.json`
**Why missing:** `BtcInfo` (the model behind `btc_info` SSE event)
doesn't include the chain name; only `BlockchainInfo` does. blitz-api
doesn't expose `BlockchainInfo` over SSE.

**Options:**

1. Streamer does a one-time REST poll of
   `/bitcoin/get-blockchain-info` at startup, caches `chain`,
   merges into every `btc_info` translation.
2. Upstream PR to add `chain` to `BtcInfo`.
3. Streamer reads `BAPI_BITCOIND_NETWORK` from the env (less
   reliable; .env may not always have it).

(1) is local + immediate. (2) is upstream-correct but slower.

### `mempool_txs` (bitcoin tile Mempool row)

**Where it's bound:** same file as above.
**Why missing:** `BTC_MEMPOOL_STATUS` is declared in `app/api/utils.py`'s
SSE constant catalogue but **nothing in the codebase actually
broadcasts it**. We mapped it in our streamer optimistically; will
fire when upstream starts emitting.

**Options:**

1. Upstream PR to add a periodic mempool broadcaster.
2. Streamer polls `/bitcoin/get-mempool-info` periodically.

(1) is upstream-correct.

## Architectural — unify plugin manifest shapes

The 3 official plugins (`electrs`, `lnbits`, `tailscale`) still use
the Phase-1 `manifest.config` map for declaring user-editable
fields. The blitz-api plugin uses Phase-3 `manifest.configSchema.fields`
(an embedded `AppManifest`).

Both work — `plugin_config_view` handles both shapes since the
post-9c fix. But the unified design intent (path A) was one shape
to learn. Migrating the 3 plugins:

- Move `config.<field>` map → `config_schema.fields[]` array.
- Same field semantics; just a structural rename.
- Each plugin gets its own commit in the official-plugins repo.
- After all 3 migrate, drop the legacy `manifest.config` parsing
  from `PluginManifest.fromJson` (one round of `dart analyze` will
  confirm no remaining consumers).

Low priority — operators don't see this, plugin authors will only
see it when adding a new plugin.
